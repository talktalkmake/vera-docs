New Tenant Setup Checklist ​

Complete every step in order. Missing any one of these will cause silent failures that are hard to diagnose after the fact.

1. Google Cloud — Service Account ​

  • [ ] Open Google Cloud Console → IAM & Admin → Service Accounts
  • [ ] Create a new service account (e.g. vera-<tenant-name>@your-project.iam.gserviceaccount.com)
  • [ ] Create a JSON key for the service account → download it
  • [ ] Copy the entire JSON contents — this becomes google_credentials_json in the tenant config

2. Google Sheets — Database Sheet ​

  • [ ] Make a copy of the VERA database template spreadsheet (or create one from scratch using the header rows in CLAUDE.md)
  • [ ] Share the database sheet with the service account email as Editor
  • [ ] Copy the spreadsheet ID from the URL (/d/<ID>/edit) → this becomes google_sheet_id
  • [ ] Confirm all 14 tabs exist with correct names (01. Time Entries … 14. Liabilities)
  • [ ] Do not share this spreadsheet with the client — it is bot-only

3. Google Sheets — Reporting Sheet (optional but recommended) ​

  • [ ] Create a separate Google Sheets file owned by you
  • [ ] Add hidden mirror sheets for each database tab using IMPORT_DB() formulas (see CLAUDE.md for exact formulas)
  • [ ] Build visible dashboard tabs on top (see CLAUDE.md for tab list and column headers)
  • [ ] Share the reporting sheet with the client as Viewer
  • [ ] The service account does NOT need access to this sheet

4. Slack — Create a Slack App ​

  • [ ] In /admin, click Create Slack app from manifest ↗ — this opens api.slack.com with all required scopes and Socket Mode pre-configured. Alternatively, go to api.slack.com/apps → Create New App → From Manifest and paste the contents of slack-manifest.json from the repo root.
  • [ ] Under OAuth & Permissions, install the app to the workspace
  • [ ] Copy the Bot User OAuth Token (xoxb-...) → slack_bot_token
  • [ ] Under Basic Information → App-Level Tokens, create a token with connections:write scope → slack_app_token (xapp-...)

Required Bot Token Scopes (canonical source: slack-manifest.json):

channels:history, channels:join, channels:read, chat:write, files:write,
groups:history, groups:read, im:history, im:read, im:write,
mpim:history, users:read, users:read.email

5. Slack — Audit Channel ​

⚠️ The bot must be explicitly invited to the audit channel. It cannot post to channels it has not joined, and failures are silent.

  • [ ] Create or identify the audit channel (e.g. #vera-audit) — can be private
  • [ ] Copy the channel ID (click the channel name → About → copy the ID starting with C) → slack_audit_channel_id
  • [ ] Invite the bot to the channel: go to the channel → type /invite @VERA (or whatever your bot's display name is)
  • [ ] Verify: after setup, trigger a test write (e.g. log a time entry) and confirm a message appears in the channel

6. Tenant Config — Add to tenants.dev.json ​

Add a new entry to the tenants file:

json
{
  "id": "acme",
  "slack_bot_token": "xoxb-...",
  "slack_app_token": "xapp-...",
  "google_sheet_id": "1ABC...",
  "google_credentials_json": "{\"type\":\"service_account\",...}",
  "timezone": "America/New_York",
  "slack_audit_channel_id": "C08ABC123"
}

Field notes:

  • id — short slug, lowercase, no spaces. Used in logs and internal routing.
  • timezone — IANA format (e.g. America/New_York, Europe/London). Controls morning/evening reminder times and snapshot scheduling.
  • slack_audit_channel_id — must be the channel ID (starts with C), not the channel name.
  • google_credentials_json — paste the full JSON as a string (escape inner quotes). In Railway, set as an env var and reference it.

7. First-time VERA interaction ​

The wizard seeds the database automatically when the tenant is created. No manual data entry is required for structural prerequisites. What the wizard inserts:

  • Disciplines: Design, Development, PM, Strategy, Admin
  • Internal client: required for overhead project categorisation
  • Default tasks: Development, Design, Admin, Meeting
  • Protected time-off projects: PTO, Sick, Leave (Internal type — required for OOO flows)

One remaining step before going live:

  • [ ] Add the Owner user: tell VERA "add user [Name] as owner with Slack ID [U...]" in a DM from that user's Slack account

8. Smoke Test ​

Go to /admin, load tenants, and click Verify next to the new tenant. The button runs five automated checks and shows a green/red result inline:

CheckWhat it proves
Slack bot token (auth.test)Bot token is valid and not revoked
Slack app token (auth.test)App token is valid and not revoked
Bot DM round-tripBot can open a DM and send/delete a message to the Owner
Audit channel postBot can post to and delete from the audit channel
Postgres round-trippg INSERT → SELECT → DELETE works for this tenant
Dashboard queryThe reporting SQL runs cleanly against this tenant's data

All six checks must be green before the tenant is considered ready. Common failures:

  • Bot DM round-trip fails with "No active owner user found" — add the Owner user first (step 7), then re-verify.
  • Audit channel post fails — the bot has not been invited to the channel. Run /invite @[botname] in the audit channel (step 5) and re-verify.
  • Slack token fails — the token was entered incorrectly or has been revoked. Update it in /admin → Save, then re-verify.

After all checks pass, optionally confirm in Slack by sending "!test morning" to trigger the morning summary DM.

9. Railway Deployment (production) ​

  • [ ] Add a new env var set in Railway for this tenant (or update TENANTS_FILE to point to a production tenants file)
  • [ ] For google_credentials_json, store as a Railway env var and reference it in the tenants JSON as "google_credentials_json": "$TENANT_ACME_GOOGLE_CREDS" — do not commit raw service account keys to git
  • [ ] Redeploy and re-run the smoke test against the production Railway URL

10. Postgres — new tenants are pg-native by default ​

All tenants created via the wizard are pg_native: true. They write directly to Postgres from the first interaction — no backfill is required and PG_SHADOW_WRITE_TENANTS does not need to include them.

The structural seed (disciplines, Internal client, tasks, protected projects) is inserted into Postgres at creation time. As soon as the Owner user is added, the tenant is fully operational.

Legacy tenants (Sheets-first): If you are migrating an existing Sheets-based tenant to Postgres, follow the original backfill steps — add the tenant id to PG_SHADOW_WRITE_TENANTS, run backfill-tenant.js, restart the service, then verify.

11. Client Dashboard — vanity URL ​

The client-facing dashboard is at https://dash.getvera.site/d/<slug>. The wizard auto-generates a 12-character base62 slug at creation time — the creation response shows it and /admin displays it in the tenant row.

  • [ ] Note the dashboard_slug from the creation response (or find it in /admin)
  • [ ] Open https://dash.getvera.site/d/<slug> in an incognito window — should render the project list
  • [ ] Share the URL with the client

The legacy URL /report/<tenant_id>/dashboard with ?token=<client_report_token> still works for backwards compatibility, but prefer the vanity URL for new tenants.
