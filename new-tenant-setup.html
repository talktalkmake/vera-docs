New Tenant Setup ​

Six steps. No Google Cloud, no Sheets, no Railway, no scripts, no restart.

1. Create the Slack app ​

Open /admin, load tenants, then click Create Slack app from manifest ↗.

This opens api.slack.com with all required scopes and Socket Mode pre-configured. On that page:

  • Click Create App
  • Select the client's workspace from the dropdown
  • Click Install to Workspace → Allow
  • Copy the Bot User OAuth Token (xoxb-…) — you'll need it in step 3
  • Under Basic Information → App-Level Tokens, click Generate Token and Scopes, add the connections:write scope, name the token anything, and click Generate — copy the token (xapp-…)

What success looks like: you have two tokens — one starting with xoxb- and one with xapp-.

2. Create the audit channel and invite the bot ​

In the client's Slack workspace:

  • Create a channel (e.g. #vera-audit) — private is fine
  • Copy the channel ID: click the channel name → About → copy the ID starting with C
  • Type /invite @[bot display name] in the channel

What success looks like: the bot appears in the channel member list.

The channel ID starts with C, not the channel name. Using the name will fail silently.

3. Create the tenant in /admin ​

Back in /admin, fill the Create new tenant form:

FieldWhere to find it
IDShort slug you choose — lowercase, hyphens OK (e.g. acme)
NameDisplay name (e.g. Acme Agency)
Slack Bot TokenThe xoxb-… token from step 1
Slack App TokenThe xapp-… token from step 1
Audit Channel IDThe C… ID from step 2
TimezoneSelect the client's timezone

Click Verify next to the Audit Channel ID field — wait for the green confirmation that the bot is in the channel. The Create tenant button stays disabled until this passes.

Click Create tenant.

What success looks like: the tenant row appears in the table and a dashboard slug is shown. The system has seeded the database automatically — disciplines, default tasks, protected time-off projects, and the Internal client are all in place.

4. Add the first owner ​

The database starts empty of people. The first owner must be added before the full smoke test will pass.

From the owner's own Slack account, open a DM with the VERA bot and send:

add user [Full Name] as owner with Slack ID [their Slack user ID]

To find a Slack user ID: click their profile → ⋮ → Copy member ID.

What success looks like: VERA confirms the user has been added. The owner can now DM VERA normally and all owner-level commands will work.

5. Verify ​

In /admin, click Verify on the new tenant row. Six checks run automatically:

CheckWhat it proves
Slack bot tokenToken is valid and not revoked
Slack app tokenToken is valid and not revoked
Bot DM round-tripBot can DM the owner and delete the message
Audit channel postBot can post to and delete from the audit channel
Postgres round-tripDatabase is reachable and write/read/delete works
Dashboard queryReporting SQL runs cleanly against this tenant's data

All six must show green. Common failures:

  • Bot DM round-trip skips or fails — add the owner user first (step 4) and re-verify
  • Audit channel fails — the bot was not invited to the channel. Run /invite @[botname] (step 2) and re-verify
  • Token fails — update the token in /admin → Save, then re-verify

What success looks like: six green checks. The tenant is fully operational.

6. Send the dashboard URL to the client ​

The dashboard URL was auto-generated when you created the tenant. It is visible in the /admin tenant row.

Format: https://dash.getvera.site/d/<slug>

Open it in an incognito window first — it should render the project list (empty at this point, which is correct). Send the URL to the client.

What success looks like: the client can open the URL without a login, sees their project list, and the page auto-refreshes every 60 seconds.

Notes ​

The database starts empty of operational data. Structural prerequisites (disciplines, tasks, time-off projects, Internal client) are seeded automatically. The first real client interaction — logging a time entry, creating a project — is the first row in the database.

Google Sheets are not required. New tenants are always Postgres-native. If you want to set up a client-facing reporting sheet using IMPORTRANGE, that is a separate, optional step and does not affect VERA's operation.

Legacy tenants (Sheets-first). If you are migrating an existing Sheets-based tenant to Postgres, that is a different process — see the docs/postgres-migration.md guide and the backfill script.
