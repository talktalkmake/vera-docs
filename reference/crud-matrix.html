VERA Object × CRUD Reliability Matrix ​

Purpose. A single map of every VERA object and the create/read/update/delete operations on it, scoped by the role that can perform each, marking which path is deterministic (no model — extractor→resolver→tool) vs probabilistic (Claude chooses the tool). This is the reference for working reliability up from the ground: every future issue, PR, and manual test should cite a cell ID (e.g. U-LOG-C) so we can pinpoint scope and track a progress bar across the whole surface.

Why this exists. The one paying client is not yet using VERA because basic actions (a user adding time) aren't yet trustworthy enough. We build confidence bottom-up: get the user role's everyday deterministic operations rock-solid first, then manager, then owner, then admin (admin == owner-level access, excluded only from team stats — see lib/roles.js).

Reads are deterministic targets. Retrieval reads ("show my time", "my hours this week", "show my envelopes", "list projects", "time for CityCore") have a fixed query shape and self-scoped or name-resolvable params — they are function calls wearing a sentence and must resolve→query→format→show without the model and without a confirm gate (a wrong read writes nothing and is self-correcting — strictly lower risk than a write). Only analytical reads that require synthesis/judgement ("how's CityCore tracking?", "am I overallocated?", "LER trend") stay probabilistic (box 2). Rule: retrieval reads = DET; analytical reads = PROB. Deterministic reads need a server-side Slack-text formatter per read verb (new lib/read-formatters.js; no existing reusable one — dashboard formatters are HTML).

How to read it.

  • Cell ID = <ROLE>-<OBJECT>-<OP>. ROLE ∈ {U=user, M=manager, O=owner}. OP ∈ {C,R,U,D}.
  • Path: DET = on the deterministic execution path today (model never invoked when fully resolved); DET* = deterministic but multi-turn wizard; DET→ = retrieval read, target for the deterministic read path (not built yet); PROB = goes through Claude (writes that need it, or analytical reads); — = not applicable / not allowed for that role.
  • Status: ✅ verified-solid (live-smoked) · 🟡 works but unproven/rough · 🔴 known-broken/issue open · ⬜ not yet assessed.
  • Verified against code 2026-06-03: endpoints in mcp-server.js, permission map checkPermission (mcp-server.js:379) + resolver VERB_PERMISSIONS (lib/entity-resolver.js), deterministic set in index.js isEligibleForDeterministicExecution (log_time, create_client, create_task) + create-project-wizard.

Scope of this first pass: the user role section is fully enumerated (that's where confidence-building starts). Manager/Owner sections list the objects and where ops live but mark status ⬜ pending their turn. We concentrate on deterministic rows first.

Deterministic path — what's actually model-free today (the verified floor) ​

Confirmed in index.js: log_time, create_client, create_task (single-turn tryDeterministicExecution), and create_project (multi-turn create-project-wizard). Everything else goes through Claude (PROB). Reads are all PROB today (no deterministic read path exists yet).

ROLE: USER (the priority — everyday, must be bulletproof) ​

A user can: log their own time, read their own time/projects, edit/delete their own entries, request time off. They cannot create/rename/delete projects, clients, tasks, users, or allocate.

User cell definitions ​

  • U-TIME-C — log own time. DET via log_time fast path (index.js isEligible + tryDeterministicExecution; extractor lib/entity-reference-extractor.js; resolver lib/entity-resolver.js). 🟡 because preposition-overload misparses still occur (on X for Y, on X on Y) and can route to the wrong project/task or fall through to PROB — see #1043 (write-confirmation gate + type-reconciliation). This is the #1 confidence target. Canonical syntax target: log <dur> on <project> for <task>, with type-based reconciliation so prepositions needn't be exact.
  • U-TIME-R — read own time. PROB. 🔴 show me time for <project> / <project> time frequently fail (no verb match → model mishandles, treats project as a person). MCP: /get_time_entries, /hours_this_week. Needs a deterministic read verb.
  • U-TIME-U — edit own entry. PROB. /edit_entry (mcp-server.js:3086; per-entry ownership check, no role gate). "actually that was 4h" / correction phrasing — unassessed.
  • U-TIME-D — delete own entry. PROB. /delete_entry (mcp-server.js:3224; ownership-checked: non-owner can only delete own). "delete that last one" — unassessed.
  • U-PROJ-R — read projects. PROB. /list_projects, /get_project_status, /get_project_info. 🟡 list projects works via model; users never see child/period rows (prompt rule). Long output may hit the scroll bug.
  • U-CLNT-R / U-TASK-R — read clients/tasks. PROB. /list_clients, /list_tasks. Unassessed for user role.
  • U-ENV-R — read own envelopes. PROB. /get_my_allocations / get_my_assignments. "what should I work on?" Unassessed.
  • U-OOO-C / U-OOO-R — request/view own time off. PROB. /request_time_off, /get_my_time_off. Users create a pending item (DMs managers); never log_time to OOO directly (business rule 14).

ROLE: MANAGER (after user is solid) — objects + locations, status ⬜ pending ​

Manager = user's abilities plus: allocate hours (own/PM projects), set budget/deadline/update for assigned projects, manage tasks for their projects, approve PTO, log time-off for others, percentage-only financial visibility. Cannot create/rename/delete projects/clients/tasks/users or assign PM (owner only).

The user's everyday loop = U-TIME-C (log) + U-TIME-R (read back) + U-ENV-R (what am I on). All three must be ✅ and model-free before the role is "trustworthy." This is the client-confidence bedrock.

Definition of ✅ for a cell: deterministic path engages on the natural phrasings (verified raw-text→real-resolver), correct write/read, receipt shown (no scroll/spinner artifact), live-smoked, and an MT exists citing the cell ID.

Conventions for issues / PRs / MTs ​

  1. Title or body must cite the cell ID(s) in scope (e.g. "U-TIME-C: confirm-gate for ambiguous time logs").
  2. An MT that proves a cell must reference the cell ID and update its Status here in the same PR.
  3. Flip a cell to ✅ only after a live smoke (the standing rule: green tests are necessary, not sufficient).
  4. Keep this file current — it is the single source of truth for the reliability progress bar.
