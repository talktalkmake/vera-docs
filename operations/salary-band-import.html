Salary Band Import Runbook ​

Use this runbook to turn published federal wage percentiles into a starting salary ladder for a discipline. There are two ways to do this, both backed by the same fetch and geographic-fallback logic (lib/wage-data.js), so they can never disagree on a result.

The normal path is the console. On the Bands tab of /console/users (/console/users?tab=bands, owner only), an owner clicks Refresh from wage data to see, per discipline, the current ladder beside what the published data proposes — and applies the ones they want, one discipline at a time. Fetching never writes. Nothing is saved until an owner clicks Apply on a specific discipline, and nothing ever runs on a schedule — see "Fetching and applying stay separate" below.

The CLI (scripts/fetch-salary-bands.js) remains available as the operator/debugging route — useful for a first-time setup check, or for diagnosing why a discipline isn't producing a proposal, without needing a browser session. It writes nothing either; it prints numbers for a human to review.

The console flow ​

  1. Set the tenant's HQ location. In /admin, find the tenant row and set HQ Location (e.g. Ann Arbor, MI). See the tenant-shape section of CLAUDE.md.
  2. Map at least one discipline to an occupation. On /console/disciplines, open a discipline's Edit modal and pick its occupation from the grouped picker. Disciplines with no mapping are skipped and listed — never guessed at.
  3. Set the CareerOneStop API credentials as process environment variables (see Prerequisites below). Without both, the Refresh button on the Bands tab doesn't appear — the page names the missing prerequisite instead of failing silently.
  4. On the Bands tab, click Refresh from wage data. Each mapped discipline gets a row: which occupation, which geography tier the numbers came from, the existing ladder, the proposed one, and an Apply button — present only when the proposal differs from what's already set.
  5. Click Apply on the disciplines you want. Each Apply writes only that discipline's ladder, through the same validation as typing the numbers in by hand. Nothing else changes until you click Apply.

A page refresh re-runs the fetch (there's nowhere to stash the proposals between requests without adding session state) — expect roughly one wage-API call per mapped discipline each time you click Refresh.

Prerequisites (both paths) ​

  1. The tenant's HQ location must be set. In /admin, find the tenant row and set HQ Location (e.g. Ann Arbor, MI). See the tenant-shape section of CLAUDE.md. For the CLI only, if it isn't set, pass --location="City, ST" on the command line instead.

  2. At least one discipline must have an occupation code mapped. On /console/disciplines, open a discipline's Edit modal and pick its occupation from the grouped picker. Disciplines with no mapping are skipped and listed — never guessed at.

  3. CareerOneStop API credentials. Register for free at https://www.careeronestop.org/Developers/WebAPI/registration.aspx, then set:

    • CAREERONESTOP_USER_ID
    • CAREERONESTOP_TOKEN

    Do not commit these anywhere, and do not add them to a tenant file — they are process environment variables only.

Running the CLI ​

node scripts/fetch-salary-bands.js --tenant=<id> [--location="Ann Arbor, MI"] [--dry-run]
  • --tenant=<id> — required, matches the tenants file.
  • --location=<..> — optional; overrides the tenant's stored hq_location for this run only.
  • --dry-run — lists which disciplines would be queried and with what location, without making any network calls or requiring API credentials. Use this to sanity-check the setup before spending an API call.

Reading the output ​

Both the console panel and the CLI report the same things per mapped discipline — the CLI prints them to the terminal:

  • The occupation title and code it queried.
  • Which geography tier the numbers came from — metro/local, state, or national. A ladder built on national numbers for a company in a small town is a legitimate answer, but you need to know that's what you're looking at before you paste it in.
  • The four raw wage anchors (10th, 25th, 75th, 90th percentile annual wage).
  • The five resulting ladder boundaries, formatted for pasting straight into the salary ladder modal on the Bands tab (floor, the three interior boundaries, ceiling).

At the end, the CLI prints a summary line: how many disciplines produced a ladder, how many were skipped or failed, and how many had no occupation mapped at all. The console panel shows the same per-discipline picture as a table instead.

The published figures are a starting point, not a verdict. Some businesses deliberately pay above the local market to win talent; some pay below it and compete on other things. Treat a proposed ladder as a first draft to sanity-check against your own pay strategy, not a number to accept unquestioned.

Why some disciplines don't get a ladder ​

The import refuses rather than approximates, on both paths. You'll see one of these reasons:

  • "no occupation mapped" — the discipline has no soc_code set. Set one on /console/disciplines and refresh or re-run.
  • "top-coded/censored value" — published wage data caps very high earners at a bound (e.g. "≥ $239,200") rather than a real figure. Arithmetic on a capped value is meaningless, so the import refuses that geography tier and tries the next broader one; if every tier is capped, the discipline is reported unavailable.
  • "no data published for this geography" — the tier is simply empty for that occupation × location (a suppressed cell). The import falls through to the next broader tier automatically.
  • A data-anomaly refusal (e.g. two percentiles came back equal) — the published figures for that geography don't support a valid ladder. This is reported directly; it does not fall through to a different tier, since the data existed but didn't make sense.
  • An HTTP or network failure — reported with the status code. The import never substitutes a different geography to paper over a transport error.

What the import never does ​

  • It never mixes geography tiers within one ladder (no splicing a national 90th onto a local 25th).
  • It never treats a capped/censored figure as if it were a real number.
  • It never guesses an occupation for an unmapped discipline.
  • It never applies a ladder without an explicit, per-discipline action — no auto-apply, no "apply all", no scheduled refresh. See "Fetching and applying stay separate" below.

Fetching and applying stay separate ​

Fetching (the CLI, and clicking Refresh on the console) only ever reads and prints or displays — it never writes to the database, calls a write endpoint, or posts to the audit channel. On the console, applying a proposal is a separate, explicit click per discipline, through the same set_discipline_ladder path a hand-typed ladder would use — so a rejected proposal fails exactly the same way a manual entry would. There is no "apply all" button and nothing runs on a schedule: a band that has been deliberately calibrated against a real pay strategy should never be silently overwritten by a data refresh.

After running the CLI ​

Copy the five printed boundaries into the discipline's salary ladder modal on the Bands tab (owner only), or re-run the same lookup from the console's Refresh button and click Apply there instead. Nothing changes until you do.
